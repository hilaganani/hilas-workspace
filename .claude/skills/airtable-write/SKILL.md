# airtable-write — יצירת רשומה חדשה בטבלת "מאגר תוכן קיים" בלבד

## עקרון מפתח: טבלה אחת, פעולה אחת

הסקיל הזה **לא** מעטפת גנרית לכתיבה ל-Airtable. הוא מוגבל באופן קשיח ל:

- **טבלה אחת בלבד**: "מאגר תוכן קיים" (`tbl1eG92lW0vsY0tc`).
- **פעולה אחת בלבד**: `POST` ליצירת רשומה חדשה.
- **לעולם לא** `PATCH`/`PUT`/`DELETE` — אין עדכון רשומה קיימת ואין מחיקה. אם צריך לתקן רשומה שגויה, זה נעשה ידנית באיירטייבל, לא דרך הסקיל הזה.
- **לעולם לא** `typecast=true` — אם ערך ל-`singleSelect` (בעיקר "קטגוריה") לא תואם **בדיוק** אחת מהאפשרויות הקיימות, הקריאה תיכשל בכוונה במקום ליצור אפשרות חדשה אוטומטית. זו הגנה מכוונת: לא ממציאים קטגוריות חדשות בטבלה של המשתמשת.

אם יש צורך עתידי לכתוב לטבלה אחרת, או לעדכן רשומה קיימת — זה שינוי מכוון לסקיל הזה (או סקיל נוסף), לא הרחבה שקטה.

## דרישות מקדימות

אותם משתני `.env` כמו ב-`airtable-read`:
- `AIRTABLE_API_KEY` — חייב לכלול גם scope `data.records:write` (לא רק `data.records:read`) עבור הבייס הזה.
- `AIRTABLE_BASE_ID`.

אם הכתיבה נכשלת ב-`403` וקריאה (`airtable-read`) עם אותו טוקן עובדת תקין — כנראה שה-scope `data.records:write` חסר בטוקן; זו בעיית הרשאה בטוקן, לא בסקיל.

## שדות הטבלה "מאגר תוכן קיים" (עודכן לאחרונה ב-2026-07-13)

| שדה | סוג | ערך בתרחיש הזה |
|---|---|---|
| `כותרת` | multilineText | כותרת המאמר בפועל |
| `קטגוריה` | singleSelect | **חובה** אחת בדיוק מ: `אוטומציות וכלים`, `מסע לקוח ואוטומציות`, `פרסום בפייסבוק/אינסטגרם`, `קורסים דיגיטליים`, `מאחורי הקלעים / אישי`, `דפי נחיתה וקמפיינים`, `פרסום ממומן - כללי` |
| `תקציר קצר` | multilineText | 1-2 משפטים תמציתיים על המאמר |
| `קישור` | multilineText | ה-URL החי המלא |
| `סטטוס` | singleSelect | `פורסם` |
| `תאריך פרסום` | date (ISO `YYYY-MM-DD`) | תאריך היום (או תאריך הפרסום בפועל אם ידוע) — נוסף ב-2026-07-13 כדי שהמאמרים יוכלו להתמיין אוטומטית מהחדש לישן, במקום גרירה ידנית בכל פעם |

**הערה**: עד 2026-07-13 היה בטבלה גם שדה `פורמט` (singleSelect, ערך קבוע `אתר`) — המשתמשת הסירה את העמודה הזו בעצמה מהטבלה באיירטייבל, ולכן היא לא מופיעה כאן יותר. אם קריאת יצירה נכשלת עם `UNKNOWN_FIELD_NAME` על שדה שכן מתועד כאן, ייתכן שהמשתמשת הסירה/שינתה שדה נוסף — רעננו את הסכימה עם ה-Metadata API (ראו `airtable-read/SKILL.md`) לפני שמנחשים שוב, ועדכנו את הטבלה הזו בהתאם.

**רשימת הקטגוריות עלולה להשתנות** — אם קריאת יצירה נכשלת עם שגיאה שמציינת ערך לא חוקי ל-`singleSelect`, רעננו את הרשימה עם ה-Metadata API (ראו `airtable-read/SKILL.md`) לפני שמנחשים שוב.

## יצירת הרשומה

```bash
python3 -c "
import json, sys
import datetime
fields = {
    'כותרת': sys.argv[1],
    'קטגוריה': sys.argv[2],
    'תקציר קצר': sys.argv[3],
    'קישור': sys.argv[4],
    'סטטוס': 'פורסם',
    'תאריך פרסום': sys.argv[5] if len(sys.argv) > 5 and sys.argv[5] else datetime.date.today().isoformat(),
}
print(json.dumps({'fields': fields}, ensure_ascii=False))
" "<כותרת>" "<קטגוריה>" "<תקציר קצר>" "<קישור>" "<תאריך פרסום YYYY-MM-DD, אופציונלי>" > /tmp/airtable-record.json

curl -s -X POST "https://api.airtable.com/v0/$AIRTABLE_BASE_ID/tbl1eG92lW0vsY0tc" \
  -H "Authorization: Bearer $AIRTABLE_API_KEY" \
  -H "Content-Type: application/json" \
  -d @/tmp/airtable-record.json | jq .
```

(שימוש ב-Python ליצירת ה-JSON, לא כתיבה ידנית של המחרוזת, כדי לא לשבור על עברית/מרכאות/תווים מיוחדים בכותרת או בתקציר.)

תגובה תקינה מחזירה אובייקט עם `id` חדש (`rec...`) ואת ה-`fields` שנשמרו — זה האישור שהרשומה נוצרה. תגובה עם `error` (למשל `INVALID_MULTIPLE_CHOICE_OPTIONS`) אומרת שהקטגוריה שנבחרה לא תואמת בדיוק לאחת האפשרויות הקיימות — יש לתקן ולנסות שוב, לא להוסיף `typecast`.

## טיפול בשגיאות

- **`401`/`403`** — טוקן שגוי/פג תוקף, או חסר scope `data.records:write`.
- **`404`** — `AIRTABLE_BASE_ID` שגוי, או ה-Table ID `tbl1eG92lW0vsY0tc` השתנה/נמחק (נדיר — רעננו מול `airtable-read`).
- **`422` עם `INVALID_MULTIPLE_CHOICE_OPTIONS`** — הערך שנשלח ל-`קטגוריה` או `סטטוס` לא תואם אף אפשרות קיימת בדיוק (כולל רגישות לרווחים/איות). לתקן את הערך, לא להוסיף `typecast`.

## מה הסקיל הזה לא עושה

לא קורא רשומות (לזה יש `airtable-read`), לא מעדכן רשומה קיימת, לא מוחק, לא נוגע בשום טבלה חוץ מ"מאגר תוכן קיים", ולא בודק כפילויות לפני יצירה — כל דיווח על מאמר שעלה לאוויר יוצר רשומה חדשה, גם אם דווח בעבר על אותו לינק.

**מיקום הרשומה בטבלה**: ה-REST API של Airtable תמיד מוסיף רשומה חדשה **בתחתית** אחסון הטבלה — אין דרך ב-API ליצור אותה במיקום ספציפי. עד 2026-07-13 המשמעות הייתה גרירה ידנית כדי שהמאמר החדש יופיע ראשון. באותו תאריך נוסף שדה `תאריך פרסום` (ראו טבלת השדות למעלה) בדיוק בשביל זה: אם קובעים **פעם אחת** באיירטייבל שהתצוגה (View) ממוינת יורד לפי `תאריך פרסום`, כל רשומה חדשה עם השדה הזה מלא תתמיין אוטומטית למקום הנכון בתצוגה, בלי גרירה ידנית — גם אם היא עדיין מאוחסנת פיזית בתחתית הטבלה. קביעת מיון התצוגה עצמה היא הגדרה ידנית חד-פעמית באיירטייבל (אין ל-API הזה יכולת לקבוע מיון תצוגה).
