This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Does

**CreativeAgent** is a multi-agent content & creative suite. **רועי (Roi)** is the CEO/orchestrator — he never does the work himself, he routes a request to the right team member(s) (in parallel when a task spans domains) and returns one unified report. Full spec: [`PRD-roi.md`](PRD-roi.md), persona: [`.claude/agents/roi.md`](.claude/agents/roi.md).

**When to dispatch Roi, and when not to** (changed 2026-07-31 — he was previously the *mandatory* entry point for every request, which made small asks slow):

- **Through Roi** — work that genuinely needs orchestrating: a monthly content plan, an article that needs SEO + writing + images, anything spanning two or more domains, or a request matching a predefined workflow in `.claude/workflows/`.
- **Directly, in the main session** — a caption, one post, an edit, a rewrite, a translation, a factual lookup, a small fix. Read the same source files the relevant persona would read (`noga/style-guide.md` and `noga/reference/`, `yael/strategy.md`, `merav/brand-guidelines.md`, `content-production-checklist.md`) and call the same skills. The personas' knowledge lives in those files, not in the agent definitions — nothing is lost by working directly.

Routing a one-step task through Roi costs a full dispatch round-trip and buys nothing. When in doubt, ask whether more than one domain is actually involved; if not, do it directly.

The team is planned at **7 people total**; **6 are built and active today** (Liat, Noga, Merav, Dani, Yael, Gefen). The 7th, **בר (Bar)** — LinkedIn marketing — is a named, real roadmap slot, not a generic placeholder, but has no persona file yet; Roi stops and reports instead of inventing this role.

(Note: an earlier, unrelated "Yael" — a marketing copywriter who dispatched an image-generation agent called Yuval — existed briefly in this project's early planning and was fully deleted; the Yael built today is a distinct role that happens to reuse the name.)

### Yael's strategic gate (before any brand-new content topic)

Before Roi kicks off production on a **brand-new content topic** (not a plain rewrite/edit/translate/summarize of content that already exists), he checks whether that topic is already pre-approved as part of one of Yael's existing monthly content plans (`yael/outputs/`). If not, he dispatches **Yael** first with the topic/brief. She returns one of three verdicts — fits the strategy (mapped to a service/customer-journey stage/goal), needs adjustment to the angle, or calls for a new strategic move entirely — before anything else runs. A "needs a new strategic move" verdict gets surfaced to the user before Roi proceeds; it never blocks silently. Once a topic is approved (or already covered by a monthly plan), the rest of the pipeline below runs as usual. Yael can also be dispatched on her own to build a full monthly content plan across social/newsletter/website.

### New content pipeline (research → write → visual)

When a request is about creating new content sourced from the internet:

1. Roi dispatches **Liat** to find a quality source on the requested marketing/automation topic.
2. Liat returns a file saved in `Content/`.
3. If the original request also asked for **rewriting/publishing** — Roi continues automatically:
   - Dispatches **Noga** on that file.
   - Noga's report specifies which image(s) the piece needs — Roi dispatches **Merav** with that brief.
   - Roi combines everything into `output/`.
4. If the request was only **"find me an article"** — Roi stops after Liat and returns her findings to the user.

Noga can also be dispatched directly (without Liat) whenever the request is to write a newsletter/blog post/social post from a brief, or to rewrite/edit/translate/summarize content that's already available — she doesn't require Liat to have run first. Merav can also be dispatched directly whenever a request is purely about generating a content image.

### Content production checklist (cross-cutting QA standard)

[`content-production-checklist.md`](content-production-checklist.md) is a shared, cross-agent QA standard built directly from a real audit of a published article's failures (wrong dashes, gendered language, keyword-stuffed sentences, a dead CTA, a broken/mismatched link, a tracking parameter that would have miscounted signups, a missing hero image, an internal note left visible in the body). It covers four things: language/keyword/story rules, a link-and-CTA checklist (including the `?cs=blog-[name]` signup-tracking parameter — never copy a `?cs=instagram` or other channel's value into a blog link), SEO delivery requirements (meta length, five FAQs, author credit), and image rules split by type — **functional graphics** (diagrams/infographics: brand palette locked, Heebo/Assistant fonts, RTL flow) vs. **hero photos** (color free, no forced brand palette, so the blog archive doesn't turn into a wall of identical purple), plus an AI-image defect checklist (watermarks, fabricated logos/marks, finger count, readable gibberish text) and format/weight rules (JPG for photography, PNG for diagrams, 1200×630 JPG for share images, resolution/weight ceilings). Noga, Dani, and Merav each read the sections relevant to their own step (see their persona files) before finishing any website/blog article, and the file's part ד' pre-delivery checklist is the last gate before Roi reports a piece as ready — an unfilled `<div class="todo">` box (used when a required real customer story or a not-yet-known link isn't available — never invented) means the piece isn't done yet.

### Noga ↔ Merav connection (article with images)

When Roi receives a request to create an article/post that needs images, the full loop is:

1. Roi dispatches **Noga** to write the piece.
2. While writing, Noga marks every place an image is needed with a `{{IMAGE_NEEDED: "detailed description, including desired style for Merav"}}` placeholder directly in her `.md` output — she does not generate images herself.
3. Noga reports back to Roi: a summary of what she wrote, plus the full list of every `{{IMAGE_NEEDED: ...}}` placeholder she left.
4. Roi dispatches **Merav** with those placeholder descriptions as image briefs.
5. Roi takes Merav's generated images and combines them into Noga's `.md` and `.html` files, replacing each placeholder with the corresponding image.
6. Roi saves the final, combined version to `output/`.

### Dani ↔ Noga connection (SEO for website/LinkedIn content)

When Roi receives a request to write a blog/website article or a LinkedIn post (not Facebook/Instagram/TikTok), the full loop is:

1. Roi dispatches **Dani** first, with the topic/brief (and Liat's research file, if any). Dani researches live, checks the existing-content Airtable table (read-only, via `airtable-read`) for already-published articles related to the topic, and returns a pre-writing SEO brief: primary/secondary keywords, title options, recommended heading structure, target length, **specific internal-link suggestions** (named article + link, with a note on where it fits naturally in the text) — not generic "add internal links" advice — and **readability targets** modeled on the Yoast plugin: at most 25% of sentences over 15 words, at most 10% of sentences in passive voice.
2. Roi folds that SEO brief into the brief it hands to **Noga**, who writes as usual (including `{{IMAGE_NEEDED}}` placeholders where relevant) — the named internal-link suggestions let her weave a natural, in-text reference to the related piece, not just a bolted-on link, and the readability targets shape her sentences from the start rather than being a post-hoc fix.
3. Once Noga is done, Roi dispatches **Dani** again with Noga's final `.md`, this time to review it against his own pre-writing brief (including whether the suggested internal links actually got used, and whether the draft's actual sentence-length/passive-voice ratios meet the readability targets) and re-check the existing-content table for anything missed, producing a publish-ready SEO package: SEO title, meta description, URL slug, keywords used, alt-text suggestions per image, **inbound internal-link opportunities** (existing published articles from the same table that would benefit from adding a link *to* this new one — the site has dozens of articles, so this is checked in both directions, not just outbound from the new piece), and non-blocking improvement notes.
4. Dani saves that package to `dani/outputs/<name>-seo.md`, then embeds just the publishing part of it (SEO title, meta description, slug, keywords, alt-texts) into the bottom of the article's own `.html` via the **`seo-package-embed`** skill — as a clearly-marked block after `</main>`, so the user sees the publishing instructions in the same file she reads the article in rather than hunting for a separate file. The `dani/outputs/` file stays the full source of truth (it also holds the internal-link verification, readability numbers, and improvement notes, which are QA records and are deliberately *not* embedded). Dani then reports both to Roi.
5. If the piece also needs images, Roi continues the Noga ↔ Merav loop above and combines everything — text, images, and Dani's SEO package — into one report and into `output/`.
6. Dani's improvement notes are suggestions only — Roi never sends Noga back for an automatic rewrite; the notes are surfaced to the user, who decides whether to request changes.

Dani can also be dispatched directly, without Noga, for a pure SEO consult or keyword research request, or for any of his five standalone skills (technical audit, content refresh, competitor analysis, topical planning, roadmap) — see `.claude/agents/dani.md` for exactly how each of those runs.

### Publish report → content log (Dani, Airtable write)

When the user reports in chat that an article is **already live on the site** (typically with the live URL, phrased like "it's live", "I published it") — this is a distinct trigger, separate from the SEO brief/review loop above. Roi dispatches **Dani** with just the live link; Dani logs it as a new record in the "existing content" Airtable table via the `airtable-write` skill (create-only — never an update to an existing record, never any other table). Dani sources the title/summary/category himself (from a matching local file in `output/`/`dani/outputs/`, or by fetching the live page directly if no local match exists) — the user only needs to provide the link. ### Tamar (sales proposals) — dispatched directly, never through Roi

**תמר** writes sales proposals. Hila comes out of a sales call, pastes a **transcript and/or a short brief**, and Tamar returns a draft ready to paste into Prospero: background, what's included, **what's excluded**, timeline, price table, payment terms. She's also a sounding board for a single question ("what goes in the exclusions for a CRM project?") without a transcript. This is single-domain work, so it's dispatched directly — routing it through Roi buys nothing.

Her job is knowing *which* proposal to give, **not whether to take the work**. If Hila reached the proposal stage, there's a proposal to write. Capacity or mix problems surface as a flag at the top of the file; they never block the draft.

Three things make it work, and each is a separate source of truth:

- **The catalog** is the `מוצרים` table in the **Mini CRM base (`appcfuP4ufqhwipBm`) — not the base `AIRTABLE_BASE_ID` points at**, read live via the `crm-deals` skill. It was realigned and written on 25.8.2026 (15 products, all priced). **A product with no price is one Hila does not sell** — never offer it and never invent a price; mark `[[להשלים]]` and ask. [`tamar/product-details.md`](tamar/product-details.md) carries what the table has no field for: delivery type, delivery hours, and what's included/excluded per product — the raw material for the proposal's "included"/"excluded" sections. Where it disagrees with the table on price, the table wins.
- **The rules** live in [`tamar/pricing-rules.md`](tamar/pricing-rules.md) — everything with no Airtable field: the 15%-of-media formula, the automation retainer/hour-bank (one product, 5,000 ₪ for 12 hours), payment terms, the never-offset rule for אפיון, capacity, delivery hours per product, and an explicit list of what is **not known** (project hours above all). A missing number that would enter a binding clause is marked `[[להשלים]]` — never invented. Discounts (max 15%) are Hila's alone and are **never mentioned in a proposal**; the agent narrows scope instead. When Hila does approve one, it is recorded in the deal's `אחוז הנחה` field rather than by lowering `מחיר העסקה`, which stays the catalog price — `מחיר אחרי הנחה` and `כולל מע"מ` derive from it, and the 15% ceiling is enforced in the skill.
- **Past proposals** in `tamar/proposals/`, indexed by service type. Structure and wording are reused — **prices never are**. A deal that closed cheap doesn't make the price right.

**Profitability is part of the job.** Each product carries a delivery type — shelf / semi-custom / custom. The Airtable mini-CRM is a shelf product: the system is already built, one אפיון meeting and it's done, so it's highly profitable. When several products answer the client's need, **a shelf product wins over a custom build**, even at a similar price — it's the only kind that doesn't hit the hours ceiling.

**Airtable writes happen only after Hila confirms in chat that the proposal was actually sent** — a draft is not a deal (same pattern as Dani logging an article only once it's live). The `crm-deals` skill hard-blocks every SUMIT/payment/materials/meeting field, because Hila's existing automations own those.

Tamar also holds the road to **100,000 ₪/month** and surfaces when the mix itself needs to change — without declaring the target impossible. The known gap: 3 concurrent build projects yield ~20,000 ₪/month, not the 60,000 ₪ the plan assumes, and the hours are nearly full before them. Shelf products are the lever.

Binary images cannot go through that connector practically — encoding an image as base64 to pass through an LLM context is prohibitively expensive — so any agent with `Bash` access (Merav, Noga, Yael, Dani) uploads images itself via the **`drive-upload`** skill — Roi has no `Bash` access (deliberate, see "Weekly plan email & approval gate" below), so he relays a Drive-upload request to one of those agents, or to the main session, rather than running the skill himself, which streams the file straight from disk to the Drive API without the content ever passing through an LLM context. Uses OAuth as the user herself, not a service account — service accounts have no storage quota on a personal (non-Workspace) Drive and cannot upload at all, confirmed the hard way. Requires `GOOGLE_DRIVE_OAUTH_TOKEN_FILE` (created by a one-time interactive `scripts/drive_oauth_setup.py` run, token file kept outside git under `/credentials/`) in `.env` — see `.claude/skills/drive-upload/SKILL.md` for the full one-time setup (OAuth consent screen, Desktop OAuth client, browser authorization). Optional; without it, agents fall back to reporting local file paths only.

**For text deliverables, Drive receives only the rendered `.pdf`** — never the `.md` or `.html`, which stay local as working files. This is because Drive shows `.html` as raw source rather than rendering it (a fixed Google security behavior, not something the upload can change), so the PDF is the only version that actually displays; the md/html copies were clutter the user never opened. Render the PDF with the **`html-to-pdf`** skill, then upload just that file. (Set 2026-07-28, narrowing an earlier rule that uploaded all three.) Image deliverables are unaffected and keep their own conventions. Uploads go to the Drive folder matching the content (a course's own folder, `dani-outputs`, etc.), not to one flat catch-all. Local `.md`/`.html` paths still get cited in chat alongside the Drive link.

## Running

Roi, Liat, Noga, Merav, Dani, Yael, and Gefen are all dispatched as subagents (no dedicated slash commands yet — see `PRD-roi.md` open questions for a possible future `/roi` command).

## Weekly plan email & approval gate

A recurring scheduled task (`weekly-content-plan-email`, cron `0 7 * * 4` — every Thursday ~7am local) runs outside any single chat session: it reads Yael's current monthly plan (`yael/outputs/<YYYY-MM>-content-plan.md`), extracts the concrete items for the upcoming calendar week, asks **Roi** to prepare a concise Hebrew summary (Roi is explicitly told this is preview-only — he must not dispatch Liat/Dani/Noga/Merav), and sends that summary as an HTML email via the `email-send` skill. If there's no plan covering the upcoming week, or the required `.env` vars aren't set, the run skips sending quietly rather than inventing content or failing loudly (nobody is watching an unattended run live).

This is a preview step only — **there is no email-reply-parsing capability**, so approval can never arrive through the email itself. Production only starts when the user comes back and explicitly approves in a live chat message (e.g. "אישרתי", "תתחילו על השבוע הבא") — that message is the trigger for Roi to dispatch `yael`, who hands off the approved week's items to the relevant employees per her plan.

Because Roi's own toolset stays orchestration-only (no `Bash`, no direct API/MCP access — see `.claude/agents/roi.md` for his exact tool grant and its scoping), the actual email send happens at the scheduling layer that invokes him, not inside Roi's persona — this was a deliberate choice to avoid widening his tool access for a single feature.

## Feedback loop: plan vs. actual

Full design: [`docs/superpowers/specs/2026-07-15-content-feedback-loop-design.md`](docs/superpowers/specs/2026-07-15-content-feedback-loop-design.md). Closes the loop between Yael's monthly plans and what Hila actually publishes, changes, or skips, reusing the existing (previously idle) "תכנון תוכן חודשי" Airtable table (`tbl86pJ76WWc3moL2`) as the single source of truth — no new database or dashboard.

When Yael finalizes a monthly plan, she also creates one row per content item (Instagram Stories excluded — they don't go through the full plan→create→publish flow) in that table via the `airtable-content-calendar` skill's create-only action, each starting at status `מתוכנן`. A recurring scheduled task (`biweekly-content-feedback-email`, every two weeks, Thursdays 7am local — same cadence as the weekly plan email, gated by an ISO-week-parity check in its own prompt since cron has no native biweekly primitive) reads rows still `מתוכנן` past their target date and asks Roi to draft a neutrally-worded digest ("items waiting for a status update," never "overdue"), sent via `email-send`. When Hila replies in a live chat (never by email reply — there's no inbox-reading capability, same constraint as the weekly plan email) with something like "1-published, 2-changed (did a different version), 3-didn't go up," Roi maps her reply to the table's own Autonumber field and dispatches the generic catch-all agent — deliberately not Yael, and not one of the seven roster employees — to run the skill's restricted update action, which can only ever touch the `סטטוס`/`הערה`/`קישור/גרסה סופית` fields. Yael stays a strategy-and-learning layer: she reads the accumulated history back in (never runs the update herself) when building the next monthly plan, and folds any recurring pattern (a channel/format that keeps getting skipped or changed) into that plan's frequency reasoning as inline prose — there is no separate stored "insight" record yet, by design (see the spec's "פערים מדעת" section for when that would change).
