# Phase 2 — Architecture Review: Current CreativeAgent

Audit date: 2026-07-14. Read-only — no files modified as part of this phase. Scope: Roi, all 6 built agents, all skills, MCP servers, tool permissions, folder structure, workflows, routing logic, shared resources, memory, config files.

## 1. Current-state inventory

- **Agents**: 7 persona files in `.claude/agents/` — `roi.md` (orchestrator) + 6 built workers (`liat`, `noga`, `merav`, `dani`, `yael`, `gefen`). One planned, unbuilt slot (`bar`), which the [Marketing OS Audit](../MARKETING-OS-AUDIT.md) already recommends against building as a 7th persona.
- **Skills**: 46 entries in `.claude/skills/`, of which:
  - **17 are CreativeAgent-domain skills**: `airtable-read`, `airtable-write`, `docx-export`, `email-send`, `google-search-console`, `gpt-image-gen`, `smoove-newsletter`, and the 10-skill `seo-*` library.
  - **~17 are generic Claude Code meta-skills** unrelated to CreativeAgent's domain (`brainstorming`, `writing-plans`, `systematic-debugging`, `test-driven-development`, `using-superpowers`, etc.) — these ship with/alongside Claude Code itself, not authored for this project.
  - **12 are community-installed skills** (`remotion-*`, `mediabunny`, `frontend-design`, `excalidraw-diagram`, `find-skills`, `web-design-guidelines`), symlinked from `.agents/skills/` via a separate installer (`skills-lock.json`), added this session but not yet wired to any agent.
- **MCP servers connected in this environment**: Airtable (used only indirectly via the hand-rolled REST skills, not the MCP directly), Google Drive, Canva, Make/Integromat, plus this session's scheduling/task infrastructure. Of these, only Google Drive has any wiring in progress (folders created, not yet connected to an agent); Canva was evaluated and rejected; Make was evaluated and paused.
- **Routing logic**: one markdown table in `CLAUDE.md` (Hebrew/English trigger keywords → agent slug), duplicated in spirit (not exact text) inside `roi.md`'s own persona and `PRD-roi.md`.
- **Config**: none, in the structured-data sense. Every behavioral rule — routing, workflow order, dependency ordering, tool scoping, output paths — lives as **prose inside markdown persona files**. There is no YAML/JSON workflow definition anywhere in the project today.
- **Memory**: no project-level structured memory system. What exists is ad hoc per-agent: Liat's `liat/Memory/searches.md` (30-day dedup log, one agent only), Airtable tables used as external structured state for content tracking, and this Claude Code session's own auto-memory system (`~/.claude/.../memory/`, cross-session, but general-purpose and not CreativeAgent-domain-structured).

## 2. Strengths

- **Context-centric agent boundaries are already correct.** Per the Phase 1 research, agents are split by domain/context (research, writing, visuals, SEO, strategy, platform-specific), not by pipeline stage. This is the pattern Anthropic's own guidance recommends and is not something this redesign should disturb.
- **Tool scoping is unusually disciplined for a project this size.** Every agent's tool list is minimal and justified (Noga has zero API access except one narrowly-scoped Smoove skill; Dani's Bash is enumerated to five specific uses; Roi himself has no Bash at all, by explicit design). This is a real strength — most of the "unnecessary complexity" risk that shows up in bigger multi-agent systems (over-privileged agents, sprawling tool grants) has been actively avoided here.
- **Consistent "propose, don't act" boundary on side-effecting operations.** Every irreversible/visible action in the system (Airtable writes, Smoove sends, biometric photo use, publish-log entries) already has an explicit human-confirmation gate baked into the relevant persona, not bolted on. This is exactly the "verification subagent" and "human-in-the-loop checkpoint" pattern Phase 1's research flags as best practice — it emerged organically here rather than being designed in from a framework.
- **The manager/supervisor pattern is already correctly chosen** (per Phase 1's OpenAI Agents SDK comparison) — Roi dispatches and synthesizes, nothing hands off control permanently. This is the right choice for a system that must always produce one unified report to the user.
- **New capabilities have consistently arrived as skills/integrations, not new agents** — the 10-skill Dani SEO library, Search Console, Smoove — validating the "prefer capabilities over agents" principle this whole redesign is also being asked to honor.

## 3. Weaknesses, duplication, bottlenecks

- **Routing logic is duplicated across at least three documents** (`CLAUDE.md`'s roster table, `roi.md`'s own persona text, `PRD-roi.md`). This was directly observed this session: every agent addition required consistent hand-edits across multiple files, with no single source of truth and no mechanism to catch drift between them. This is the clearest, most concrete "duplicated logic" finding in the audit.
- **Multi-step workflows are held together entirely by Roi's own working memory within a single dispatch, not by any persistent structure.** The Dani ↔ Noga two-pass loop, the Noga ↔ Merav placeholder-fill loop, and Yael's strategic gate all depend on Roi (a fresh subagent instance each time it's invoked) correctly remembering to re-dispatch Dani a second time, correctly collecting Merav's file paths and threading them back into Noga's output, etc. **There is no persisted workflow state** — if a session is interrupted mid-pipeline (e.g., between Dani's pre-write brief and Noga's draft), nothing records that the pipeline is "in progress" or what stage it's at; recovery depends on the user or Roi reconstructing intent from chat history.
- **No structured retry policy anywhere.** If Merav's `gpt-image-2` call fails, if a Search Console API call 500s, if Noga's output is missing a required section — there is no defined "try again N times with backoff" behavior. Recovery is currently "the agent notices and reports it in prose," which is fine for a chat-driven system today but does not scale to any future automated/scheduled execution.
- **No QA/verification step exists as a distinct concern.** Dani's post-write review is the closest thing to a quality gate, but it is domain-specific (SEO only) and has no authority to block — "non-blocking notes only" is repeated as an explicit rule everywhere. There is no general-purpose "does this deliverable actually meet the brief" check independent of any one agent's own domain lens. Per Phase 1's research, this is exactly the kind of concern that should be a dedicated, minimal-context verifier — not something layered onto an already-specialized agent.
- **Config-as-prose makes correctness unverifiable except by careful reading.** Because every rule (which agent runs when, in what order, with what data) lives in natural-language persona files, there is no way to *validate* a workflow definition — a contradiction between `CLAUDE.md` and an agent's own persona file is only caught by a human (or Claude) reading both closely, exactly as happened multiple times this session (e.g., discovering `noga.md`'s "no Bash" claim needed updating in three separate places when Smoove access was added).
- **The flat `.claude/skills/` namespace mixes three unrelated categories** (CreativeAgent-domain skills, generic Claude Code meta-skills, community-installed skills) with no separation. Not a functional bug today (Claude Code doesn't require separation), but a discoverability/scalability concern as the domain-skill count keeps growing — Dani alone already owns 11 of the 17 domain skills.

## 4. Unnecessary complexity (things to *not* add, flagged pre-emptively)

- The user's brief for Phases 4–6 describes DAG execution, timeout handling, cancellation, and resumable workflows in terms that echo Temporal/Durable Functions. Per Phase 1's research and Anthropic's own explicit guidance (3–10x token cost per added coordination layer), **building a general-purpose durable-execution engine would be disproportionate** to a system that runs, at most, a handful of workflow instances per week, entirely inside human-paced chat sessions. Phase 5 designs the lightest structure that actually satisfies the named requirements, not the heaviest one that resembles the frameworks studied.
- There is no evidence CreativeAgent currently needs true parallel *workflow instances* (two content pipelines running simultaneously, independent of each other) — today's "parallel" need is exclusively fan-out/fan-in *within* one workflow (e.g., Merav generating 3 images at once). Designing for multi-tenant concurrent workflow execution now would be solving a problem that doesn't exist yet.

## 5. Scalability issues

- **Roi's context grows with every new agent and workflow**, since routing knowledge lives entirely in his persona prose. At 6 agents this is manageable; at 12+ (with video, voice, publishing, analytics agents as flagged in the user's Phase 7 prompt) the routing table and workflow descriptions inside `roi.md` will become unwieldy to read and error-prone to keep in sync — this is the concrete case *for* moving routing to structured config (Phase 6), not an abstract one.
- **Dani's skill count (11 of 46 total, 11 of 17 domain-specific) is already the largest concentration in the project.** This isn't a problem today (all 11 are read via progressive disclosure, not all loaded at once), but it's worth flagging as the first place a "should this agent be split" question will arise if it keeps growing (Phase 7 addresses this directly).
- **No versioning or changelog for skills/workflows.** A skill can change behavior with no record of *why* beyond a git commit message. For a "long-term AI operating system," workflow definitions in particular (once they exist as config, per Phase 6) should be versioned so a broken change is traceable and revertible independent of code changes.

## 6. Missing capabilities (cross-reference with the Marketing OS Audit)

Re-confirming findings already established in `MARKETING-OS-AUDIT.md` from an orchestration lens specifically:
- No performance-feedback loop closes back into planning (Search Console now exists for Dani, but nothing routes that signal into Yael's monthly planning automatically — it's still a manual "Dani mentions it, human decides" step).
- No structured way to know a workflow **completed successfully** vs. **partially completed** — today "done" means "Roi said so in its final report," which is a prose claim, not a checked condition.
- No cross-agent memory of what's already been tried/decided (a "campaigns," "hooks," or "what worked" memory — addressed in Phase 8).

## 7. Future risks

- **Drift between documentation and behavior.** As routing/workflow logic keeps living in prose across multiple files, the risk of `CLAUDE.md` saying one thing and an agent's actual persona doing another grows with every edit — already observed once this session.
- **Silent partial failures.** Without retry/checkpoint structure, a workflow that fails at step 3 of 5 currently just... stops, with the user having to notice and manually restart from scratch (redoing steps 1–2 unnecessarily). This gets worse, not better, as workflows get longer (e.g., a future video-generation step added to the pipeline).
- **Unbounded agent-count growth without a forcing function.** Nothing in the current architecture prevents "add a new agent" from being the default answer to "we need capability X," other than convention and this project's own stated preference. Phase 6/7 make the alternative (add a skill/tool to an existing agent) the structurally easier path, not just the documented preference.

This review deliberately makes no changes. Phases 4–9 build directly on the strengths identified here (context-centric agents, disciplined tool scoping, manager pattern, human-in-the-loop gates) while addressing the weaknesses (duplicated routing logic, no persisted workflow state, no retry policy, no general QA step, prose-only config) using the patterns validated in Phase 1 — sized to this project's actual scale, not the scale of the frameworks studied.
